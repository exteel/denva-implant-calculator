# DENVA AI — Калькулятор імплантації v2: архітектура

Джерело вимог: `docs/TZ_v2_DENVA_AI.txt`. Рішення власника (13.10.2026):
Supabase як бекенд · строго за новим ТЗ (без Q00, порівняння пропозиції, рівнів впевненості,
CTA CheckMyPlan/КТ/Tender) · головна валюта — гривня, еквівалент у EUR · Telegram-бот ще треба створити.

## 1. Загальна схема

```
                    ┌──────────── GitHub Pages (статичний Next.js) ────────────┐
 Пацієнт ──────────►│ /            лендінг                                      │
                    │ /calculator/ калькулятор (формули в браузері)             │
 Адміністратор ────►│ /admin/      адмінпанель (вхід через Supabase Auth)       │
                    └───────┬──────────────────────────────┬────────────────────┘
                            │ читає лише public_prices     │ адмін-запити (RLS)
                            ▼                              ▼
                    ┌──────────────────────── Supabase ─────────────────────────┐
                    │ Postgres: міста, клініки, послуги, прайси, ручні орієнтири,│
                    │   агрегати (snapshots), published_prices, audit_log, leads │
                    │ SQL-функції: перерахунок → публікація (черга + pg_cron)    │
                    │ Edge Functions: submit-lead → Telegram; nbu-rate (щодня)   │
                    └────────────────────────────────────────────────────────────┘
```

- Ціни **не зберігаються у frontend-коді** (ТЗ §2): калькулятор завантажує опубліковані ціни
  міста (≈30 рядків) з API й рахує формули в браузері — тому сума оновлюється миттєво при
  будь-якому перемикачі (ТЗ §6.1). Прайси клінік фронтенд не бачить (RLS).
- Адмінпанель — частина того самого застосунку, працює повністю в браузері; права перевіряє база
  (Row Level Security): без ролі адміністратора жоден запис не змінити.
- Секрети (токен Telegram-бота) живуть лише в Supabase, не в коді сайту.

## 2. Модель даних (ТЗ §2.1)

| Таблиця | Ключові поля |
|---|---|
| `regions` | id, name, active — регіональний fallback |
| `cities` | id, name, region_id, currency, active, aliases, min_clinics (null → глобальний поріг) |
| `services` | service_code, name, role, unit, tiered, included_text, active, sort |
| `clinics` | id, name, city_id, network_id, status (draft/active/excluded), verified_at, contacts |
| `clinic_prices` | id, clinic_id, service_code, tier, price_from, price_to, value (= середина діапазону), currency, offer_name, brand_material, included_text, exclusions, valid_from, verified_at, status (pending/approved/rejected/stale), include_in_aggregate, exclude_reason, source_url, document_path, import_batch_id |
| `city_manual_prices` | city_id, service_code, tier, value (+ value_from/value_to) |
| `region_manual_prices` | region_id, service_code, tier, value |
| `price_modes` | city_id, service_code, tier, mode: `auto` \| `manual` \| `manual_override` |
| `city_aggregates` | snapshot: city_id, service_code, tier, value, clinic_count, method, included_ids, excluded (з причинами), calculated_at — **лише додаються, не перезаписуються** |
| `published_prices` | city_id, service_code, tier, value, currency, source_type (`aggregate` \| `manual` \| `manual_override` \| `regional_fallback`), source_id, clinic_count, calculated_at, published_at; історія — `published_price_history` |
| `settings` | min_clinics = 3, aggregation_method = median, stale_after_months = 12 |
| `currency_rates` | currency, rate_to_uah, rate_date (НБУ) |
| `import_batches` | файл, автор, протокол імпорту |
| `audit_log` | хто, що, старе/нове значення, причина, коли (тригери на всіх адмін-таблицях) |
| `leads` | payload (jsonb), phone, city, telegram_status, error, attempts, created_at |

Рівні (`tier`): `common` (Спільний), `minimum`, `classic`, `premium`.
Рівневі ролі: implant, crown, arch_final. Решта (healing, scan, superstructure, multiunit,
arch_temp, temporary, addon) — `common`.

## 3. Агрегація та публікація (ТЗ §2.2–2.3, §3)

**Вибірка** для (місто, service_code, tier): клініка `active` у цьому місті · ціна `approved`,
`include_in_aggregate`, не старша за `stale_after_months` · валюту нормалізовано за курсом на
дату розрахунку · **одна клініка = один голос** (найсвіжіший запис) · **філії однієї мережі з
однаковою ціною = одне джерело**.

**Розрахунок:** median (за замовчуванням) або arithmetic_mean — з `settings`. Кожен
перерахунок пише новий snapshot у `city_aggregates` (з переліком включених і виключених
записів і причинами).

**Публікація** (пріоритет ТЗ §2.3):
1. `manual_override` → ручне значення міста;
2. агрегат, якщо clinic_count ≥ порогу (3) і режим не `manual`;
3. ручний міський орієнтир;
4. регіональний орієнтир → `regional_fallback` («середня ціна регіону»);
5. інакше рядка немає → калькулятор пише «даних поки недостатньо» (суму не вигадує).

**Події перерахунку** (ТЗ §3.3): тригери на `clinic_prices`, `clinics`, `price_modes`,
`city_manual_prices`, `region_manual_prices`, `settings`, `currency_rates` кладуть у чергу
**лише зачеплені** комбінації (місто × service_code × tier); `pg_cron` щохвилини обробляє чергу.
Перерахунок ідемпотентний; поки новий не завершився успішно, діє попередня опублікована ціна.

## 4. Формули (ТЗ §4) — `src/engine/formulas.ts`

- **1 зуб:** implant[it] + healing + scan + superstructure + crown[ct].
- **Протезування на встановленому імпланті:** superstructure + crown[ct] + scan.
- **Сусідні 2–6:** таблиця ТЗ §4.2 (2→2 імпл./2 кор., 3→2/3, 4→2/4, 5→3/5, 6→3/6), scan один раз.
- **Окремі місця 2–6:** n × (implant + healing + superstructure + crown) + scan.
- **Змішано / не знаю (2–6):** діапазон «міст … окремі імпланти» з поясненням.
- **7+:** порівняння сегментного сценарію з All-on-4/6/8 (див. відкрите питання А).
- **Повна щелепа:** перший етап = N×implant[it] + N×multiunit + arch_temp + scan;
  повне = перший етап + arch_final[pt] + scan. Дві щелепи — усе подвоюється, крім scan (один
  запис на етап). Головна цифра — перший етап (ТЗ §6.2).
- **Додаткові процедури** (видалення, аугментація, синус, м’які тканини, седація, тимчасова
  коронка, навігаційний шаблон) — окремий блок, ніколи не в total.
- Валюта: сума в гривні, нижче еквівалент у EUR за курсом НБУ з датою.

## 5. Екрани (ТЗ §5–6)

1. **Місто** — логотип DENVA AI, «Калькулятор імплантації», пошук (список після 1–2 літер),
   «Немає мого міста → оберіть область».
2. **«Які зуби потрібно замінити імплантами?»** — 4 варіанти; «Окремі зуби» розкриває на тому
   самому екрані бігунок 1·2·3·4·5·6·7+ (свайп / мишка / тап), далі лише кнопкою «Продовжити».
3. **Одне уточнення за гілкою** (ТЗ §5.3).
4. **Результат одразу** — 3 картки-пресети (Мінімальний / Класичний / Преміальний), у вибраній
   — незалежні перемикачі рівня імпланта і коронки (для щелепи — постійної конструкції); сума,
   еквівалент EUR, деталізація, місто й дата цін, джерело («на основі прайсів N клінік» /
   «статистичний орієнтир Denva» / «середня ціна регіону»), можливі додаткові витрати,
   застереження про консультацію та КТ. Параметри (кількість, розташування, All-on-X, щелепи)
   можна змінити просто на сторінці результату.
5. **Заявка під результатом** (не модальне вікно): «Уточнити мій розрахунок» + «Надіслати мені
   розрахунок і список запитань для консультації»; лише телефон, без SMS. Заявка спершу
   зберігається в базі, потім іде в Telegram; помилка Telegram не блокує результат — кнопка
   «Надіслати ще раз». Payload готовий для Planfix у наступній версії.

## 6. Адмінпанель (ТЗ §7) — `/admin/`

Міста та регіони · Клініки · Каталог послуг · Прайси клінік (вручну + імпорт Excel) ·
Міські орієнтири (сітка minimum/classic/premium по кожній послузі) · Агрегати міста (вибірка,
метод, аномалії, fallback, опубліковане значення) · Історія змін · Заявки · Налаштування.

- **Excel-шаблон «DENVA шаблон цін клініки»** генерується з адмінки; імпорт створює чернетки
  зі статусом «На перевірці» й повертає протокол (прийняті, помилки, дублікати, невідомі
  service_code, очікують модерації). До підтвердження модератором на калькулятор не впливає.
- Контроль якості: попередження про відхилення від чинного агрегату, показ включених і
  виключених записів з причинами, журнал змін.

## 7. Перевірки

- Формули й екрани: Vitest + Playwright (як у v1).
- SQL-логіка (агрегація, «один голос», філії, пріоритет публікації, fallback, черга):
  тести на **PGlite** (Postgres у npm, Docker не потрібен).
- Деплой: сайт — GitHub Actions → Pages; база й функції — `supabase db push` /
  `supabase functions deploy` після того, як ви створите проєкт.

## 8. Що потрібно від власника

1. Створити проєкт на supabase.com і виконати в терміналі `npx supabase login` (відкриє браузер).
2. Створити Telegram-бота через @BotFather і додати його в робочий чат; токен вписати в
   секрети Supabase (інструкцію надам).
3. Створити свій акаунт адміністратора (інструкцію надам).

## 9. Відкриті питання

- **А. 7+ зубів.** ТЗ: «залежить від схеми — порівняти сегментний міст і All-on-4/6/8».
  Пропозиція: сегментний референс «4 імпланти + 7 коронок» (позначений як орієнтир) поруч з
  All-on-4/6/8 для однієї щелепи; для обох щелеп — All-on для двох щелеп.
- **Б. Уточнення для «Не знаю».** Пропозиція: «Скільки приблизно зубів відсутні або
  потребують видалення?» — 1 / кілька / більшість на щелепі / не знаю; останнє → довідкова
  ціна одного зуба.
- **В. Початкові дані.** Поки ваших прайсів немає — заллю поточні демо-значення як ручні міські
  орієнтири з позначкою «демо».
